# Engineering foundations for Tropical Futures dashboard

Research date: 2026-09-26. Scope: canonical engineering methods, inspection of the supplied dashboard, and a proposed Claude-compatible improvement process. This is research and static code inspection. No dashboard source was changed; no build, test suite, browser verification, plugin installation, connector authentication, or optimization experiment was run.

## What do Compound Engineering and Karpathy autoresearch actually contribute?

### Takeaway
Use Compound Engineering for the outer delivery process and an adapted autoresearch loop for narrowly scoped, measurable improvements. Karpathy's original project optimizes language-model training; applying its structure to a commerce dashboard is our proposed adaptation, not a claim that the original repository already evaluates dashboards.

### Cited Findings
- The canonical Compound Engineering project is EveryInc/compound-engineering-plugin. Its documented current sequence is brainstorm, plan, work, simplify, review, compound. The Claude Code install instructions use the EveryInc marketplace and compound-engineering plugin. The main benefit for this project is retaining useful reasoning between changes. The source was read from its current main branch; it was not installed or version-pinned here. — [Official repository README](https://github.com/EveryInc/compound-engineering-plugin)
- The dedicated compound guide says to document verified, durable, non-obvious knowledge in docs/solutions; machine-enforceable lessons belong in tests/types/assertions, local rationale in comments, and shared terminology in CONCEPTS.md. It explicitly says not every completed change needs a separate learning document. — [Official ce-compound guide](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/guides/ce-compound.md)
- Karpathy's repository is a single-GPU language-model training experiment. Its deliberately small boundary separates fixed preparation/evaluation code, editable train.py, and human-written program.md. Training receives a fixed five-minute wall-clock budget and is judged on validation bits per byte, lower being better. Those are ML-specific choices. — [Karpathy's original repository](https://github.com/karpathy/autoresearch)
- Its program establishes a baseline, protects the evaluator, records candidate results, keeps improvements and discards failures; simplicity matters as well as score. The original instructions permit indefinite iteration once started. We should adopt the experimental structure but set a finite dashboard batch budget, not inherit its open-ended execution instruction. — [Original program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)

### Inferences
- For Tropical Futures, compound engineering should preserve domain invariants such as “consigned goods are still brand-owned,” “a reported sale is not a remittance,” “Shopify revenue is not bank cash,” and “unknown sessions cannot become observed conversion.” These are proposals informed by the commerce-model weaknesses below; the commerce researcher should refine their exact operational definitions.
- An autoresearch-style candidate should be a small UI, query, import, or explanation change with fixed input data and observable success. “Make the dashboard best” is too broad to be a defensible optimization objective.
- The dashboard's existing park-rating number is not a valid engineering evaluation target: changing weights can increase the score without improving decisions. Founder judgment must remain decisive for brand character, tone, legibility, and whether a deliberately limited drop should be replenished.

### Gaps
- The plugin is not callable as an installed skill in this research session, and installed status in the user's Claude environment was not checked. We can apply its documented method without claiming the plugin ran.
- No experimental baseline, task-completion measurement, or outcome improvement has been measured yet. No source promises these methods will produce a universally “best” dashboard.
- Current upstream main/master documents can change. Pin the chosen upstream version or commit when the implementation process is established.

## How should the next phase work through Claude?

### Takeaway
Proposed architecture: a standalone web dashboard and Claude Desktop as two interfaces to one persistent service, with Claude Code maintaining that application. This is a recommendation reported by the coordinator, not a confirmed user decision or an implemented connection.

### Inferences
All items below are proposed work, not completed implementation.

#### Architecture brief
- Keep one versioned domain model and calculation service. Both dashboard and Claude obtain totals from it; Claude explains figures with source IDs, timeframe, currency, freshness, and assumptions rather than recomputing from a prompt.
- Give Claude useful read tools first: business brief, SKU stock by location/ownership, overdue receivables, consignment settlement status, and explanation of a metric. Provide source drill-down in the dashboard.
- Persist manual and imported records in a local database with backup/export, or a private hosted service if multi-device use is needed. Select local stdio versus authenticated remote MCP after the Claude surface and hosting preference are confirmed.
- Later scoped operations, such as recording a consignment report or partial payment, should use typed inputs, validation, audit history, idempotency keys, and an explicit draft/review/commit boundary appropriate to the operation. Repeated reports must not double-count units or remittances. Credentials belong server-side. External actions like issuing refunds, editing inventory, sending invoices, or changing ad budgets are a separate capability decision.
- Maintain a short CLAUDE.md pointing to domain vocabulary, metric definitions, brand MD, decision records, test commands, integration contracts, and prior durable lessons. Do not make it an oversized dump of all research.

#### Bounded improvement process
1. Ingest the brand MD and reconcile it with public research. Record verified brand constraints, founder vocabulary, decision priorities, and open questions. Do not bake unverified fixture values into the specification.
2. Baseline the existing app in isolation: build/lint, specific defect reproductions above, keyboard tasks, source-freshness display, storage behavior. Preserve screenshots and measured outcomes.
3. Write a versioned evaluation contract separate from editable app files. Freeze fixture data, clock, expected calculations, task instructions, and gate thresholds for a batch. Have a separate evaluator retain a holdout set with different dates, SKUs, partners, and failure combinations.
4. Form one falsifiable hypothesis per candidate, name the allowed files and exact user task, then plan/build/simplify/review. An initial proposed batch limit is up to six candidates or 60 minutes, whichever comes first; adjust after measuring baseline runtime. Avoid changing business rules and visual hierarchy in the same experiment.
5. Apply hard gates before ranking: exact financial/inventory reconciliation to fixture expectations; correct provenance/freshness and honest missing-data labels; persistence and duplicate-report handling; keyboard completion, focus/dialog behavior, readable zoom/reduced motion; correct completion of every critical task; no unauthorized external writes or leaked credentials; build/lint and relevant regression checks.
6. Rank only candidates that pass all gates. Measure critical-task errors first, then founder task-completion time and interaction steps; report performance changes separately. Do not collapse correctness and appearance into a weighted score that allows a prettier mistake to win. Changes with no meaningful gain should require a clear simplification benefit.
7. Run the untouched holdout only at promotion, with a reviewer who did not implement the candidate. An observed failure becomes a future regression fixture; rotate fresh holdouts for the next batch rather than repeatedly tuning to the same hidden answers.
8. Record hypothesis, revision, fixture/evaluator versions, baseline, candidate outcomes, gate results, holdout result, time/cost, complexity, and keep/discard/error reason. Keep failures in the record. Never change fixtures/thresholds to rescue a candidate, remove difficult tasks, or call LLM self-ratings objective measurements.
9. Have the founder judge brand fit and decision usefulness with representative realistic data. Promote only a passing, reviewed candidate; capture durable lessons in the narrowest useful home, following the Compound Engineering guidance. Stop the batch at its budget and report what actually improved.

#### Priority order after brand MD
- **P0: truth and data safety.** Fix misleading freshness, synthetic visitor/refund presentation, weak import validation, shelf-edit loss, and inaccurate LIVE/time labels. Add the smallest meaningful regression cases.
